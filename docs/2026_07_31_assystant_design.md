# assystant — design spec

Date: 2026-07-31
Author: Han Lin Mai

## Goal

A lightweight command-line utility that runs an ASSYST campaign end to end — from a
system specification (species, stoichiometries, maximum cell size, spacegroup range)
through PyXtal structure generation, DFT relaxation and permutation sampling, to a
single collated training dataset — driven by the current release of `pyiron_workflow`.

This replaces the current practice of copying `2025_03_16_Unaries.py` per campaign,
hardcoding element lists in notebook cells, and hand-maintaining `submit_temp.sh`
with one `calculate_assyst.py` invocation per element.

## Background: what exists today

Two halves, currently spread across notebooks and ad-hoc scripts in
`/u/hmai/2024_12_05_DFTPyxtalAssystNodes`:

**Structure generation** — `2025_08_31_PyxtalUnaryGen.ipynb` and
`2025_05_01_PyxtalBinaryGeneration.ipynb`. A PyXtal scan over spacegroups 1–230
crossed with composition tuples, volume-rescaled to a band around an equilibrium
volume per atom drawn from `EleBulk_MatProj_VorVol.csv`, written out as
`{idx}_structure.vasp` POSCARs under `<root>/<system>/structures/`.

**DFT campaign** — `calculate_assyst.py` reads those POSCARs and, per structure,
builds a `pyiron_workflow` graph (`run_ASSYST_on_structure`), pickles it, writes an
sbatch script that unpickles and runs it, and submits. The graph runs an
ISIF7 → ISIF5 → ISIF2 relaxation chain, keeps the SCF-converged images, then runs
high-accuracy statics on those base structures plus rattle/triaxial/shear
permutations of them, concatenating everything into `df_ASSYST_jobs.pkl`.

**Monitoring** is `2025_04_03_CheckPyxtalJobStatus.ipynb`, which counts
`struct_pyxtal_*` directories against directories containing `df_ASSYST_jobs.pkl`
and appends to `job_progress.csv`.

## The pyiron_workflow 0.19 problem

The installed stack targets `pyiron_workflow` 0.11. The current release is 0.19.0,
which is a rewrite rather than a rename. `pyiron_workflow` is now only a runtime;
the graph description language is a separate hard dependency, `flowrep`.

Concretely, every construct the current ASSYST code is built on has moved or gone:

| 0.11 | 0.19 |
|---|---|
| `@Workflow.wrap.as_function_node`, `@pwf.as_function_node` | `@fr.atomic` (plain functions also parse) |
| `@pwf.as_macro_node` with leading `wf` arg | `@fr.workflow`, no `wf` arg, plain Python body parsed from AST |
| `wf.a = f(wf.b.outputs.x)` | `wf.a = pwf.node(f)` plus explicit `wf.connect(...)` / `EdgeTuple` |
| `for_node(f, zip_on=("a","b"), ...)` | a real `for a, b in zip(as_, bs_):` loop inside `@fr.workflow` |
| `pwf.inputs_to_list(n, ...)` | accumulator list, or `TransformNto1` |
| `pwf.standard_nodes.Length` | removed; no direct equivalent |
| `node.outputs.result` | `run.outputs.<port>`; default port name is `output_0` |
| `wf.save(backend="pickle")`, `PickleStorage` | **removed entirely**; no replacement API |
| `node.run()` mutates node state | `run(node, config, **inputs)` returns a `Run` |

Other breaking semantics: Python 3.11–3.13 only; locally-defined functions are
rejected (`<locals>` in qualname raises `ImportError`); node labels inside graphs are
auto-generated by flowrep (`vasp_job_0`, `for_each_0`, `body_3`) rather than
hand-chosen; DAG layers are multithreaded by default; edge type validation is on by
default.

Requires a fresh conda environment — 0.19 needs `pyiron_snippets>=1.3`, and the
existing envs carry 0.1.4 and 0.2.0.

## Architecture: three repositories

`assystant` stays thin. The pyiron-layer work happens in the two existing
`ligerzero-ai` repos, which need the 0.19 port regardless of this tool.

```
pyiron_workflow_vasp   (port to 0.19)   VASP nodes + parsers
          ^
pyiron_workflow_assyst (port to 0.19)   the ASSYST graph + structure filters
          ^
assystant              (new, thin)      campaign: config, generation, submission,
                                        status, collection
```

### Repo 1 — `pyiron_workflow_vasp` → 0.19

2661 lines, of which only the decorated layer touches `pyiron_workflow`:

- `vasp.py` — 9 decorated functions: `create_WorkingDirectory`, `write_VaspInputSet`,
  `parse_VaspOutput`, `check_convergence`, `generate_VaspInput`, `get_multiple_input`,
  `generate_modified_incar`, `construct_sequential_VaspInput_from_vaspoutput_structure`,
  and the one macro `vasp_job`.
- `generic.py` — 5 decorated functions (`shell`, `isLineInFile`,
  `delete_files_recursively`, `compress_directory`, `remove_dir`), plus
  `submit_to_slurm`.
- `vasp_parser/` (`outcar.py` 1282 lines, `output.py` 550 lines) — **untouched**.
  Pure pymatgen/numpy/monty/scipy, no `pyiron_workflow` import anywhere.

Function nodes become `@fr.atomic`; `vasp_job` becomes `@fr.workflow`. The plain
helpers (`VaspInput`, `write_POSCAR`/`INCAR`/`POTCAR`/`KPOINTS`,
`read_potcar_config`, `stack_element_string`, `get_default_POTCAR_paths`) are already
undecorated and carry over unchanged.

Two deletions:

- `get_multiple_input(obj, n=...)` is **removed**. It existed only to broadcast a
  scalar (an INCAR, a POTCAR path list) across the N inputs of a `for_node`. `ForEach`
  broadcasts non-iterated inputs to every body automatically, so the whole
  `Length` → `get_multiple_input` → `generate_VaspInputs` pattern disappears.
- `submit_to_slurm` is **removed** from this repo. It imports `PickleStorage`, which
  no longer exists, and job submission is `assystant`'s concern. Moving it out
  restores a clean separation: this repo describes VASP work, `assystant` decides
  how it reaches a scheduler.

### Repo 2 — `pyiron_workflow_assyst` → 0.19

- `structure_filter_utils.py` — no pyiron dependency; changes are bug fixes only
  (below).
- `workflow.py` — `run_ASSYST_on_structure` is rewritten as `@fr.workflow`. Because
  flowrep parses the function body as ordinary Python, the ISIF7 → ISIF5 → ISIF2
  chain reads as straight sequential code, and the two `for_node(..., zip_on=...)`
  fan-outs become real `for ... in zip(...)` loops with accumulator lists. Combined
  with dropping `get_multiple_input`/`Length`/`inputs_to_list`, the graph should end
  up materially shorter than the current 507 lines.

Constraints to design the rewrite around: `@fr.workflow` bodies permit exactly one
`return`, forbid reassignment of parent-scope variables inside loops, require
iteration sources to be plain symbols rather than inline expressions, and build loop
outputs through the `results = []; results.append(...)` accumulator pattern.

### Repo 3 — `assystant` (new)

```
assystant/
  config.py      YAML -> CampaignConfig, flag overrides, provenance dump
  cli.py         gen | run | status | collect
  generate.py    PyXtal scan -> structures/*.vasp + manifest.csv
  incar.py       INCAR assembly + MAGMOM string
  submit.py      sbatch rendering, squeue introspection, idempotent skip
  status.py      progress table + CSV log
  collect.py     walk campaign -> concatenated dataset
```

Dependencies: `pyiron_workflow>=0.19`, `flowrep`, `pyiron_workflow_assyst`,
`pyiron_workflow_vasp`, `pyxtal`, `pymatgen`, `ase`, `pandas`, `pyyaml`.

## CLI surface

`assystant gen camp.yaml` — runs the PyXtal spacegroup × stoichiometry scan and
writes `<root>/<system>/structures/{i}_structure.vasp` plus `manifest.csv`
(index, structure hash, spacegroup, composition, atom count, volume per atom). The
manifest is new; it is what lets `status` and `collect` report on provenance rather
than counting directories, and its hash column is what names the per-structure run
directories.

`assystant run camp.yaml [--ntasks N] [--time HH:MM:SS] [--from-scratch] [--limit N] [--dry-run]`
— walks the manifest and, per structure, skips anything already queued
(`squeue -u $USER -o %Z`) or already carrying `df_ASSYST_jobs.pkl`, then renders and
submits one sbatch job. `--dry-run` renders scripts without submitting.

`assystant status camp.yaml [--watch] [--csv out.csv]` — per-system progress table,
optionally appended to a CSV in the same shape as the existing `job_progress.csv`.

`assystant collect camp.yaml -o out.pkl` — concatenates every `df_ASSYST_jobs.pkl`
under the campaign root into one dataset, joined against the manifest.

## Directory namespacing

Every structure in a campaign gets its own directory, and that directory's name is
derived from the structure's content, not only its index:

```
<root>/<system>/struct_<idx:05d>_<sha8>/
```

where `sha8` is the first eight hex characters of the SHA-256 of the canonical POSCAR
string. The hash is recorded as a column in `manifest.csv`.

The index alone would be unique *within* one generation pass, but not across passes.
Re-running `gen` with a different random seed produces a different structure at
index 5 while `struct_00005/` still holds a populated `executorlib_cache` keyed by
node lexical path — and since that key does not hash inputs, the stale cache would be
silently reused and return another structure's VASP results. Making the directory
name content-derived removes that failure mode by construction: a changed structure
cannot land in a populated namespace.

Two rules follow, and both are departures from the current scripts:

- **No `os.chdir`.** `calculate_assyst.py` and `2025_03_16_Unaries.py` both `chdir`
  into the structure folder and then pass relative workdirs (`job_name + "/ISIF7"`),
  so correctness depends on process working directory. All workdirs become absolute
  paths derived from `run_dir`.
- **The executorlib cache lives at `<run_dir>/executorlib_cache`**, so it is scoped
  to exactly one structure and cannot be shared between two.

`collect` reads the structure hash from the manifest to tie results back to their
generating structure. It also recognises the legacy `struct_pyxtal_<idx>` layout, so
existing campaign data on disk remains readable without migration.

## Execution and resume

One SLURM job per structure, as today: a 64-task allocation running the whole ASSYST
chain internally via `srun`, which keeps scheduler load unchanged. Inside the job the
runner calls:

```python
pwf.run(assyst_recipe, RunConfig(run_dir=struct_dir), structure=..., incar=...)
```

with `struct_dir` the absolute, content-hashed path described above.

The improvement over the current setup is resume. Attaching `NodeSingleExecutor` to
the VASP nodes places an executorlib cache under `<struct_dir>/executorlib_cache`,
keyed by node lexical path, so a job killed at the 48-hour wall and requeued skips
the VASP steps that already completed. Today a requeue restarts from ISIF7. An
`exception_hooks` entry pickles the failed `Run` for post-mortem, replacing the
debugging information previously available from the saved node.

**Cache-staleness hazard.** The executorlib cache key is the node's lexical path with
no hashing of inputs, so reusing a `run_dir` after changing an input silently returns
the previous result. The two ways that can happen are handled separately:

- *Changed structure* — handled by construction, since the directory name embeds the
  structure hash and a changed structure therefore gets a fresh, empty namespace.
- *Changed INCAR or ASSYST parameters* — the structure hash cannot catch this, so
  `run` compares the resolved config against the one recorded in the campaign
  directory and refuses to proceed on a mismatch unless `--from-scratch` is given.
  `--from-scratch` wipes `run_dir` in full, including the cache, rather than only the
  calculation directories.

Native per-node SLURM submission via `NodeSlurmExecutor` is **out of scope**. The
executor choice is confined to one seam in `submit.py` so `--executor slurm-native`
can be added later, but nothing is built for it now. The reason to defer: it would
turn roughly 4,000 jobs per binary system into roughly 64,000, and the scheduler
impact needs measuring before it is worth the parallelism gain on the ~15 statics per
structure.

## Bug fixes carried into the port

**Duplicate `RCORE` dictionary.** `structure_filter_utils.py` defines `RCORE` twice,
at roughly lines 5 and 77; the second silently wins and the first is dead code. They
disagree — the dead one is physically per-element (Ti 2.8, V 2.7, Cr 2.5 bohr), the
live one collapses many transition metals to 2.3 bohr. The live values are correct
for the `_sv`/`_pv` semicore POTCARs pyiron selects by default, so behaviour is
preserved: the dead dictionary is deleted and a comment records which POTCAR set the
remaining values correspond to.

**Minimum-image distance floor.** `get_minimum_distance` uses pymatgen's
`Structure.distance_matrix`, which applies the minimum-image convention and therefore
misses the true nearest periodic image in heavily sheared or triaxially strained
cells — a real 0.88 Å H–H contact was reported as 1.88 Å. Since ASSYST's whole
purpose is generating heavily distorted cells, this matters. The fix is an ASE
`neighbor_list`.

This **changes which permutation structures pass the filter** and is therefore not
cosmetic. It is exposed as `filters.min_dist_backend`, defaulting to `neighbor_list`,
with `mic` retained to reproduce earlier campaigns exactly. The practical effect is
confined to species where `(1 - tol) * 2 * RCORE < min_dist` — in the default
configuration, hydrogen and helium — but those are precisely the light elements where
a sub-ångström contact wrecks an SCF.

A third, smaller issue: `filter_distance_by_species` builds `structure_copy` (a
2×2×2 expansion for single-atom cells) and then never uses it, passing the original
`structure` to `_element_wise_dist`. Removing the dead variable is safe because
`_element_wise_dist` uses `get_all_neighbors`, which handles periodicity correctly.

## Testing

- **Filters** — a known sheared cell with a true sub-ångström contact that the MIC
  backend accepts and the neighbour-list backend rejects. This pins the fix and
  documents the behaviour change.
- **Config** — parsing, flag-override precedence, and the staleness check that
  compares a resolved config against a recorded one.
- **Generation** — composition enumeration for unary and multi-component systems
  (the `min_atoms <= sum(comp) <= max_atoms` filter), and manifest round-tripping.
- **Submission** — `--dry-run` renders sbatch scripts without touching the queue, so
  the submission path is inspectable in CI.
- **Ports** — the two repo ports are validated by running a single tiny structure end
  to end (one atom, low ENCUT, few ionic steps) and comparing the resulting
  `df_ASSYST_jobs.pkl` schema against one produced by the current 0.11 stack.

## Verified before implementation

A target environment was built at `/cmmc/ptmp/hmai/mambaforge/envs/assystant`:
Python 3.12.13, `pyiron_workflow` 0.19.0, `flowrep` 0.6.2, `pymatgen` 2026.7.27,
plus ase, pyxtal, pandas, pyyaml.

**The ASSYST graph shape expresses cleanly in `flowrep`.** A probe reproducing the
structure of `run_ASSYST_on_structure` — a sequential ISIF7 → ISIF5 → ISIF2 chain
feeding a collection step, then two independent fan-outs over base and permutation
structures, then a concatenation — parsed, built and ran correctly, returning the
expected 2 base and 6 permutation results. Specifically confirmed:

- Two separate `for ... in zip(...)` accumulator loops in one workflow body are fine,
  compiling to `for_each_0` and `for_each_1`.
- Subscripting a node output (`r7["struct"]`) works, auto-injecting `getitem` nodes.
- Non-iterated inputs such as `incar` broadcast into every loop body automatically,
  which is what makes `get_multiple_input`/`Length` removable.
- Literal arguments materialise as `constant_N` sibling nodes.

The parser restrictions are therefore satisfiable by a natural rewrite rather than a
contorted one. This was the largest unknown in the plan and it is now closed.

**The VASP parsers survive the version bump.** `vasp_parser/` imports and exposes
`parse_vasp_directory` under Python 3.12 with pymatgen 2026.7.27, needing no changes.
Two pieces of trivial hygiene surfaced: `outcar.py` raises `SyntaxWarning` in six
docstrings containing an unescaped `\A` (they need to be raw strings), and
`vasp_parser/__init__.py` lists `VaspParser` in `__all__` although no such name
exists, so `from vasp_parser import *` would fail.

## Remaining risks

`executorlib`'s SLURM integration is unproven in this cluster environment. The chosen
architecture depends on it only for within-job caching, not for submission, which
limits the blast radius if it misbehaves — if the cache proves unreliable the design
degrades to today's behaviour (restart from ISIF7) rather than breaking.

The `vasp_job` macro and the `check_convergence`/`parse_VaspOutput` nodes have not yet
been exercised against 0.19; the probe used stand-in nodes. Porting `vasp_job` is the
first implementation step for that reason.

Node labels inside the ported graph are auto-generated by flowrep rather than
hand-chosen, so any downstream code or notebook that reaches into the graph by label
(for instance `wf.ISIF7_job`) will need updating to the new names.

## Out of scope

- Native per-node SLURM submission (`NodeSlurmExecutor`).
- Migrating existing campaign data to the new layout — `collect` reads the current
  on-disk shape unchanged.
- Any change to the VASP parsers beyond what Python 3.12 compatibility demands.
